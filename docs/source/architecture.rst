System Architecture
===================

Overview
--------

The DARQ application separates the user interface, API and image-processing
pipeline into independent components.

The main architecture is:

::

                         User
                           |
                           v
                  +------------------+
                  | Gradio frontend  |
                  |     :7860        |
                  +--------+---------+
                           |
                           | HTTP
                           v
                  +------------------+
                  | FastAPI backend  |
                  |     :8000        |
                  +--------+---------+
                           |
                           v
                  +------------------+
                  |   Job storage    |
                  |    meta.json     |
                  +--------+---------+
                           |
                           v
                  +------------------+
                  |   DARQ worker    |
                  +--------+---------+
                           |
                           v
                  +------------------+
                  |  DARQ pipeline   |
                  +--------+---------+
                           |
                           v
                  +------------------+
                  |     Results      |
                  +------------------+

This separation prevents the web interface from being responsible for a
long-running biomedical processing task and makes the system easier to deploy,
monitor and extend.


Gradio frontend
---------------

Gradio is responsible for the user interface.

Its main responsibilities are:

* Receiving the input images.
* Receiving the subject identifier.
* Sending the input data to FastAPI.
* Receiving the generated ``job_id``.
* Polling the backend to check the processing state.
* Displaying the real-time processing progress.
* Loading and presenting the final DARQ results.

Gradio does not execute the DARQ processing pipeline directly.


FastAPI backend
---------------

FastAPI acts as the coordination layer between the frontend and the job
system.

Its main responsibilities include:

* Receiving processing requests.
* Validating and storing uploaded files.
* Creating new jobs.
* Returning job metadata and processing status.
* Exposing health and status endpoints.

The API is separated from the image-processing worker. Therefore, receiving
HTTP requests does not require FastAPI itself to execute the complete DARQ
pipeline.


Job system
----------

Each DARQ processing request creates an independent job directory.

A simplified structure is:

::

   webapp/jobs/<job_id>/
   |
   +-- input/
   +-- output/
   +-- logs/
   +-- display/
   +-- meta.json
   +-- DARQ_report.pdf

This organization provides isolation and traceability between different
processing executions.


meta.json
---------

The ``meta.json`` file acts as the shared state contract between FastAPI, the
worker and the frontend.

It stores information such as:

* Job identifier.
* Pipeline name.
* Current status.
* Creation time.
* Start time.
* Finish time.
* Processing progress.
* Generated outputs.
* Error information.

The main job lifecycle is:

::

   queued
      |
      v
   running
      |
      +----------> failed
      |
      v
   completed

Using a file-based metadata system keeps the architecture simple and allows a
job to be inspected manually without requiring an external database or
message queue.


DARQ worker
-----------

The worker is responsible for executing processing tasks.

The common worker infrastructure handles operations such as:

* Looking for queued jobs.
* Selecting jobs belonging to the corresponding pipeline.
* Updating the job state.
* Executing the processing command.
* Capturing pipeline output.
* Storing logs.
* Marking the job as completed or failed.

The DARQ-specific worker adds the configuration required to execute the DARQ
pipeline and identify the outputs generated by it.


DARQ processing pipeline
------------------------

The DARQ pipeline performs the biomedical image-processing operations.

At a high level, the current execution contains stages such as:

* Preparing the subject data.
* Preprocessing.
* DaT symmetry and mask generation.
* MRI-DaT preparation.
* MRI-DaT registration.
* Generation of quantitative and visual outputs.

The processing algorithm remains separated from the web infrastructure. This
allows the application architecture to evolve without changing the intended
biomedical processing behaviour.


Real-time progress
------------------

The progress indicator shown in the Gradio interface is connected to actual
DARQ processing events.

The progress flow is:

::

   DARQ processing
          |
          | prints processing stage
          v
   Base worker captures stdout
          |
          v
   DARQ worker identifies the stage
          |
          v
   meta.json is updated
          |
          v
   FastAPI returns current metadata
          |
          v
   Gradio polling
          |
          v
   Progress bar is updated

This design means that the progress bar represents real processing stages and
does not rely on artificial timers.


Docker Compose architecture
---------------------------

Docker Compose runs the application components as separate containers.

The current services are:

``frontend``
   Runs the Gradio user interface.

``api``
   Runs the FastAPI backend.

``worker``
   Executes DARQ processing jobs.

The containers share the required job storage so that the API, worker and
frontend can access the same processing information and outputs.


Internal communication
----------------------

Inside the Docker Compose network, services communicate using their service
names.

For example, the Gradio frontend communicates with FastAPI using:

::

   http://api:8000

The browser accesses the published Gradio port using:

::

   http://localhost:7860

This distinction is important because ``localhost`` inside a Docker container
refers to that same container rather than another Compose service.


Scalability
-----------

The architecture separates common infrastructure from DARQ-specific
processing.

This makes it possible to add other pipelines in the future by providing
their own API creation logic, client and worker while reusing the common job
management infrastructure.

Conceptually:

::

                      FastAPI
                         |
               +---------+---------+
               |         |         |
               v         v         v
             DARQ       PET       MRI
              job       job       job
               |         |         |
               v         v         v
          DARQ worker PET worker MRI worker

Independent workers would allow jobs belonging to different pipelines to run
concurrently when sufficient computational resources are available.


Design principles
-----------------

The architecture follows several main principles:

Separation of responsibilities
   Gradio presents information, FastAPI coordinates requests and the worker
   performs long-running processing.

Traceability
   Each execution has its own job directory, metadata, logs and outputs.

Modularity
   Pipeline-specific behaviour is separated from common infrastructure.

Deployability
   Docker Compose provides a reproducible way of running all required
   services.

Extensibility
   Additional processing pipelines can reuse the common API, job and worker
   concepts without redesigning the complete application.
